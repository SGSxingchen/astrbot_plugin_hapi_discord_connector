# 待审批状态权威对账与提醒去重

## 背景

HAPI 会话摘要可能保留已失活会话的历史 `pendingRequestsCount`，详情中的
`agentState.requests` 也可能暂未回收。插件不能仅凭摘要或旧 SSE 缓存把这些
对象视为仍可操作的审批。

## 生效规则

1. HAPI 原生请求以 `(session_id, request_id)` 作为稳定唯一键。
2. 只有会话详情明确仍为 `active`，且 `agentState.requests` 中仍存在该请求时，
   才能进入 HAPI 待审批集合。
3. 会话 inactive、详情为空、请求消失或详情接口返回 404 时，立即清理对应的
   本地 HAPI pending 缓存和序号；网络校验失败时不发送提醒，也不把未知状态当作
   有效请求。
4. 自动审批接口成功后立即移除本地请求，并短暂抑制 SSE 重放同一请求，直到 Hub
   不再返回该 request ID。
5. LLM 工具审批与上下文压缩属于插件本地短时流程，不计入 HAPI 原生提醒的会话数
   或全局数，也不会以 Discord 窗口 ID 作为 HAPI session 触发提醒。

## 提醒与重载

- 提醒任务发送前执行详情对账，只对有效 HAPI 原生请求发卡。
- 同一有序 `(session_id, request_id)` 集合在 `remind_interval` 窗口内只发送一次；
  集合增加、删除或更换请求后允许新的提醒。
- `SSEListener.start()` 在监听已运行时不会覆盖已登记的后台任务句柄；
  `stop()` 和插件 `terminate()` 会取消并等待所有 SSE、提醒、防抖和完成通知任务。

## Discord 展示

待审批提醒使用专用“待审批提醒”标题，正文只保留会话数量、全局数量和
`/dhapi → 审批` 入口。它不再经过权限请求的“参数 / 详情”解析，避免把正文重复
复制到 Embed 字段中。

## 验收

自动测试覆盖空队列、Hub 对账清理、请求唯一键、终态清理、inactive 会话、重复启动、
提醒节流、集合变化和提醒 Embed 去重。部署验收时还应在 HAPI 中保留一条 active
真实权限请求，确认首次提醒、审批后清除和无重复提醒三个路径。
